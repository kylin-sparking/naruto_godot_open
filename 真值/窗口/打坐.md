## ③ 身上的特效 = `healNew` 帧序列（不是 shader、不是一张图）

`Character.as:2742-2765 tickHealAnimation()`：

- 条件是 `movementAction == SIT0 || SIT1`；**不是打坐时把它从角色身上摘掉**；
- 建的是 `FrameQueueAnimation`（`mouseEnabled = mouseChildren = false`），数据 =
  `ImgUtil.getImg(ImgType.Etc,"effects")` 里的 **`healNew`**；
- 加进角色后调 `adjustLayer()` —— 层序在 `animation` 之后、`_namePane` 之前（`Character.as:1626` 那张表）；
- 每帧 `tick(param1)` 推进。

`healNew` 的真身（GameData `Etc.effects.healNew`，现查）：每一帧是
`{"value":{"className":"Effect_healNew_N","swfName":"Effect_healNew"}, "origin":{"x":…,"y":…}, "delay":…}`
—— **第 0 帧 delay = 12000**（原地那圈基础光环，一直停着），往后各帧 delay = 200 毫秒轮播，
每帧有**各自的 origin**（注册点，不是画布正中）。素材在 `swf/Effect/Effect_healNew.swf`
（同目录另有旧的 `Effect_heal.swf`，2.2.3 用的是 `healNew` 那一份）。

⇒ 移植口径和掉落物金币那次一样：**逐帧导出、按 origin 摆、AnimatedTexture 只认同尺寸 ⇒
先补成正方形画布再拼**（这条坑在 `真值/窗口/掉落物.md` §4 记过）。帧数、每帧 origin、每帧 delay
**一律从 GameData 现读**，别写死。

## ⑮ 八卦阵为什么"飘"—— 2026-10-13 定案（第三稿，**其中"盘本来就是死的"那条已被 ⑯ 推翻**）

**用户基准**：「九帧各有一块八卦阵，盘是死的、不要动；只要每帧的盘互相重叠就不会飘。」
**定案：盘本来就是死的。照原版公式摆就重叠；我加过的每一种"补偿"都是把它顶走的那只手。**

### 两条不依赖任何自动量法的硬证据

1. **原版 GameData 里这九帧只有 `origin` 与 `delay`**（现查 `<原版目录>/原版源数据/GameData.dat.json`
   的 `Etc.effects.healNew`，键 0~8，每条形如
   `{"value":{"className":"Effect_healNew_4","swfName":"Effect_healNew"},"origin":{"x":110,"y":150},"delay":200}`）
   ⇒ **没有任何每帧偏移、缩放、alpha 可漏**；原版的摆位就是 `CharacterItem.setOrigin():53-60` 的
   `bmp.x = -origin.x; bmp.y = -origin.y`。⇒ 原版盘不动，我们照同一条摆，盘也不可能动。
2. **肉眼对照**：`开发工具/放大看盘位.py` ⇒ `测试/截图/打坐/盘位放大对照.png`
   （第 0/2/4/8 帧各按注册点对齐、白十字=注册点、每 10 像素一条黄线、4 倍放大）
   ⇒ 四格里那块八边形盘相对白十字**一样高**。

### 四种"自动地标"全部不可信（都在起气那几帧被盘下面的辉光骗走，别再拿它们的数下结论）

| 量法 | 报出来的数 | 实际量到的是什么 |
|---|---|---|
| `环底距`＝最后一个 alpha>30 的像素行 | 22,22,24,26,32,29,25,24,22 | 辉光下沿 ⇒ 拿它钉平把盘往上顶最多 10 像素（第一版"越修越飘"的根因） |
| `阵底`＝最长连续亮段落在 78~108 的那些行 | 盘底离注册点 7,7,7,10,14,12,10,8,7 | 还是辉光（第 4 帧那团亮往下淌）⇒ 拿它钉 = 主动把盘抬 7 像素 ⇒ 用户看到"飘起来"（第二版的根因） |
| 整块阵 FFT 配准（覆盖率） | 九帧**全 1.000** | 那片被气糊满 ⇒ 假满分（自己加的色配对照：同色只有 0.6%~74.6%） |
| 第 0 帧盘的 RGB 花纹配准 | 九帧最佳偏移全 (0,0) | 同时报了**七帧"峰不尖"**（最佳格与周边 8 邻只差几）⇒ 分辨不出位移，"0"是假阴性 |

⇒ **通用规矩（这一族以后都按这条办）**：在"主体 + 辉光 + 气"糊在同一张位图上的素材里，
① 不许拿"找边 / 找宽 / 找亮度覆盖 / 配得上"当基准；
② 任何配准类分数必须同时报**峰尖不尖**与**能不能测出我故意造的位移**，缺一就不许写结论；
③ 定案要靠**不依赖量法的证据**：数据源本身（GameData 有没有这个字段）+ **放大到肉眼能看的对照图**。

### 二、素材侧：以第 0 帧那块阵为尺子，逐帧量盘还差多少（**这次量法带两条自检**）

库 `开发工具/盘配准.py`（对账脚本 `读回打坐九帧位.py` 与出图脚本 `叠红绿看第8帧.py` 共用它）：
把第 0 帧与第 n 帧都按注册点铺进同一张叠图，**只认画实的像素**（alpha>200，辉光半透明被切掉），
±6 搜"重叠区色差最小"的整数位移。每条都跑：

- **阳性对照**：先把第 n 帧故意压 5 像素再搜 ⇒ 必须报出 −5（八帧**全过**）；
- **峰尖度**：竖直色差曲线两端最差 ÷ 谷底 ⇒ 实测 1.25~2.95，**都是尖的**（>1.15 才算能用）。

| 帧 | 盘与第 0 帧的错位 | 结论 |
|---|---|---|
| 1 / 2 / 3 / 4 / 5 | **(0, 0)** | 一比一重合 |
| **6** | **(−2, −3)** | 这块阵比第 0 帧**偏左上** 2~3 像素 ⇒ position 该加 **(+2,+3)**（往右下挪）才重合 |
| **7** | **(−2, −3)** | 同上 |

⚠ **符号口径（我自己差点在这儿翻车）**：`盘配准` 报的 (dx,dy) 是**叠图里 `顶/左` 的量**，
而 `顶/左` 增大 = 内容往**左上**走 ⇒ 与 `position` 增量**反号**。用 `开发工具/验盘配准符号.py`
实测钉死（把第 6 帧内容整体往下搬 5 像素、工具的 dy 跟着 **+5**）。
⇒ 一律取库给的 `position修正`（已反好号），别拿 `应加` 直接加到 position 上。

挪错方向会比不挪更糟（盘往反方向跳 4~6 像素）。

⇒ **用户看到的"最后那一两帧会动、幅度不大"是真的，而且就是第 6、7 两帧**（他先让删的第 8 帧同类）。

原版 `FrameQueueAnimation.generateCharacterItem()` 每帧都是 `ci.setOrigin(该帧自己的 origin)`
（`FrameQueueAnimation.as:56-70` + `CharacterItem.as:53-60`）⇒ 原版播到这两帧时盘同样跳 2~3 像素。

### 三、"编辑器里不飘"为什么与这不矛盾

编辑器里是**静态逐帧切**（或勾 `全显` 看叠影），2~3 像素在视口缩放 + 无参照物的情况下看不出来；
游戏里是**每 200 毫秒连续换帧**，同一块盘突然挪 2~3 像素正好落在运动感知最敏感的区间。
⇒ 所以"编辑器不飘"不能当"摆位没错"的证据，反之"游戏里飘"也不能当"运行期在抖"的证据 ——
**两件事要分别量**（这一节就是先量了运行期、再量素材，才把话对上）。

## ⑰ 真凶：视口是奇数时整幅画面落在半像素上 —— "全屏就飘、默认窗口不飘"（2026-10-13 收口）

### 现象与排查顺序（每一步都是实测，不是推断）

1. 用户报"你启动游戏实测没有飘动，我进入游戏就有了"⇒ 先排掉两份工程：另一份
   `<原版目录>/naruto_godot` 里**根本没有**打坐光环的 .gd/.json/.tscn ⇒ 他跑的就是整合版。
2. 排"换帧有没有隐藏前一帧"：`开发工具/查打坐换帧亮几帧.gd` 进真地图打坐、逐引擎帧普查
   ⇒ **1500 拍全部只亮 1 帧**（含 8 次换帧那一拍），场景贴图子节点 8 个 == 帧表 8 帧 ⇒ 没有漏网节点。
   顺带把"帧表管不到的节点永远不会被隐藏"这个真风险钉进了门。
3. 用户自己给出关键线索：**"恢复到默认分辨率就不飘了，我之前一直全屏"**、
   **"我的全屏有窗口栏"**、**"会不会不是 1920×1080 而是 1908×1080"** ⇒ 方向转到**视口尺寸**。

### 根因（一行算式）

```
屏幕位 = 世界 − 相机 + 视口/2
```
`脚本/地图/世界相机.gd` 原来是 `global_position = _clamp_center_to_map(期望中心).round()`
—— 按**世界像素**取整。**视口宽或高一旦是奇数**（带标题栏的"窗口化全屏/最大化"客户区经常是奇数），
`视口/2` 就带 `.5` ⇒ 每个世界像素被推到两个屏幕像素**正中间** ⇒ 工程是 Nearest 采样
（`default_texture_filter=0`）⇒ 光栅化逐帧在两边各取一次整 ⇒ **整幅画面抖**，
而八卦阵那种**细亮线**最显眼 ⇒ 看起来就是"盘在飘"。身体是实心块，抖 1 像素不易察觉。

### 对照实测（`开发工具/查全屏抖不抖.gd`，同一环境只改窗口尺寸）

| 相机写法 | 视口 | 画布偏移 | 屏幕位小数 | 抖不抖 |
|---|---|---|---|---|
| 老写法 | 960×560（偶） | (−39.0, 100.0) | 0.00 | 不抖 |
| **老写法** | **961×561（奇）** | **(−39.5, 99.5)** | **0.50** | **抖** |
| 老写法 | 1920×1080（我这台机器的全屏，偶） | (−39.0, 100.0) | 0.00 | 不抖 ⇒ 我这复现不出，用户那是带栏全屏 |
| **新写法** | 960×560 / 961×561 / 1023×767 | 全整数 | **全 0.00** | **不抖** |

⇒ 判据必须是**"屏幕位的小数部分"**，不是"屏幕位有没有多值"——半像素偏移时位置数值照样恒定，
只看"有没有多值"会当场判成"不抖"（我第一版就栽在这儿，靠**回退到老写法做对照**才抓出来）。

### 修复（一行，对偶数视口零行为变化）

```gdscript
var 半视口: Vector2 = get_viewport_rect().size * 0.5 / zoom
global_position = (_clamp_center_to_map(desired_center) - 半视口).round() + 半视口
```
⇒ `屏幕位 = 世界 − round(世界 − 视口/2)` ⇒ **恒为整数**。
视口为偶数时 `视口/2` 本身是整数 ⇒ 与老写法逐像素等价 ⇒ **零行为变化**（不会动到已验收的画面）。

### 门

`测试/相机屏幕像素对齐回归测试.gd`（**有头**，判 11 / 红 0）：三档视口（960×560、961×561、1023×767）
逐一判"角色注册点屏幕位小数 == 0"与"画布偏移小数 == 0"，最后一条判
"相机位置的小数 == 半视口的小数" ⇒ 这一条就是**阳性对照**（老写法下相机小数 0、半视口 .5 ⇒ 必红）。
⚠ 故意**不进** `验证全部.ps1` 的全量清单：那份统一 `--headless`，而无头下改 `root.size` 视口不变
⇒ 三档会变成同一档、判据恒真 = 假绿。

### 影响范围（别只当成打坐的事）

这条治的是**整个世界层**：任何半透明细线素材（八卦阵、连斩底图、技能格选中流光、
滚动条那根 1px 亮线）在奇数视口下都会抖。⇒ 以后凡是"某特效在某个窗口大小下才抖/糊"，
**先量屏幕位的小数部分**，再怀疑素材。
