### 变异当场抓出的五条「门自身 / 工具自身」的毛病（比代码 bug 更值得记）
1. **`_查(左 <= 0.0 …)` 这种"边界写松了"的判据，等于没判**：L4（把整串居中的那句改成 `0.0`）第一次跑是**绿的**
   —— 因为 `0.0 <= 0.0` 成立。⇒ 改成"串的中点必须落在 0 附近"（`absf((首+尾)/2) < 0.5`），L4 才响。
   教训与 `N28 / M23` 同族：**判据的容差要卡到"坏行为一定越界"，不能只卡方向。**
2. **判据里裸用 `收数[收数.size() - 1]` ⇒ 变异把那一支打掉时数组是空的 ⇒ 运行期报错 ⇒ 协程死掉 ⇒ 门永不退出（超时 300 秒）**：
   P3 第一次跑就是"超时"，既不是通过也不是红。⇒ 换成 `收数.count(0) == 1`（空数组也安全），
   并把这条拆成"解出发没发 0"+"喂 0 面板该收起"两条。**任何"读数组最后一个"的判据都要有出口。**
3. **`--check-only` 对引用了 autoload 的文件必然报假错**：L11 落点是 `玩家.gd`（里面写了 `GameSession.current_map_id`），
   命令行编译期看不见 autoload ⇒ 变异工具那道"变异先过 parse 自检"直接判 `parse坏`、变异根本没跑。
   ⇒ 现在对 `玩家.gd` 这一类落点**跳过 parse 自检**（真错会让门超时，仍然看得出），并在日志里写明为什么跳。
4. **量具把两个同名节点同时留在树上会自己骗自己**：⑩ 那段先 `new()` 了一个独立玩家（`_ready` 里 `add_to_group("player")`），
