## ② 条在屏幕上的位置

`positionWindow():176-188` ⇒ `x = round((STAGE_WIDTH − width)/2)`、`y = 0` —— **顶部水平居中**，
不是贴在左上角头像旁边。拖动过之后（`hasCustomPosition`）才保持原位并被 `keepWindowInStage()` 钳进屏内。
本工程用 `anchor_left=anchor_right=0.5` + `offset_left=-116 / right=116 / top=0`，与算式同形。

## ③ 血蓝条（`MBar.as` 逐行）

元件内部（`元件时间轴.py MBarHPF --树`，MPF 只差 `bar` 那张皮）：
`barBg`#568 @(45,2)｜`maskMc`#509 @(48,4)｜`bar`#790(血)/#570(蓝) @(48,4)｜`tf`#571 @(47,3)｜`label`#166 @(2,2)

天然尺寸（ffdec 导出实测）：`barBg` **135×12**、`bar` **129×7**、`maskMc` **129×7**（与 bar 同一张形状）。

`DetailsWindow` 的调用序（hp 先 `setBarStartXToZero` 后 `width`，mp 反过来 —— 两条算出来一样）：

1. `setBarStartXToZero():90-99` ⇒ `barBg.x = tf.x = 0`、`bar.x = maskMc.x = (135−129)>>1 = 3`（**y 不动**）
2. `width = 113`（`set width():76-83`）⇒ 差量 `135−129 = 6` 保持不变 ⇒ `barBg.width = tf.width = 113`、
   `bar.width = maskMc.width = 107`
3. `setData(当前,上限):128-175` ⇒ 比例 `r = 当前/上限`，`bar.x` 目标 = `0 + (113−107)>>1 − int(107·(1−r)) = 3 − int(107·(1−r))`，
   用 `TweenLite.to(bar, 0.5, {x})` **补间 0.5 秒**。bar 被 `maskMc`（钉在 x=3、宽 107）裁 ⇒
   可见部分 = 从 x=3 起、宽 `round(107·r)` —— **左端对齐、右边收缩**。

⇒ Godot 侧 `TextureProgressBar`：矩形 (3,4) 107×7（条局部）= 全局 (65,23)/(65,35)，
`fill_mode = 0`（BEGINNING）、`min 0 / max 1`、`step 0.001`、`tint_progress=false`、
`texture_progress = 血条填充.png`。

⚠ **10-15 订正（原来这段写错了，用户实机图打回）**：原文写的是"129×7 摆在 107 的控件里，
引擎横向压到 107"—— **`TextureProgressBar` 不缩放贴图**，而且它默认 `ignore_texture_size = false`
⇒ 贴图的天然尺寸会**把控件自己撑大**（偏移算出来是 107，运行期 `size.x` 变成 129），
于是条往右戳出面板 22 像素。真值只有一个数：**贴图天然宽 = 控件宽 = 107**
⇒ 素材按 Flash 的 `bar.width = 107` 重烘（`开发工具/烘信息条填充.py`，129→107 逐列双线性）。
判据钉的是**真值那个 107**，不是"贴图宽 == 控件宽"（后者恒真 = 假判据，变异实测抓出来的）。

同理另一处坑：`TextureRect` 的 `StretchMode` 在 4.7 里 **`STRETCH_SCALE = 0`**、`TILE = 1`、
`KEEP = 2`、`KEEP_CENTERED = 3`、`KEEP_ASPECT = 4`（实测量出来的，不是文档那个顺序）。
条底板（`条底板.png` 135×12 摆在 113×12）要的是**非等比压**（Flash `barBg.width = 113` 就是压）
⇒ `stretch_mode = 0`；写成 `3` 是"原尺寸居中"= 两头各溢出 11 像素，比 `4`（等比）更糟。

换算成条局部坐标（`_hpBar` 在 (62,19)）：

| 件 | 条局部矩形 | 皮 |
|---|---|---|
| 血条底 | (62,21,113,12) | `条底板.png` 135×12 **横向压到 113**（Flash 的 `barBg.width=113` 就是压） |
| 血条 | (65,23,107,7) | `血条填充.png` |
| 血字 | (62,22,113,18) | `tf`#571：**10px SimSun 白色、水平居中**、`MBar.as:58-59` 把高钉成 18 并加黑辉光 |
| 蓝条底 / 蓝条 / 蓝字 | y 各 +12 | `蓝条填充.png` |

文案 = `MBar.as:163` `param1 + "/" + param2`（`showPercent` 默认 false）⇒ 条上印的是 **`650/650`**，不是百分数。
`当前 == -1` 或 `上限 == -1` ⇒ 印 `?/?`（`:158-161`），这一档给 `type == 2`（NPC）用：
`setData():241-246` 对 NPC 先 `setBarStartXToZero()` 再 `setData(-1,-1)`。

⚠ **原版笔误**：`setMp():207-210` 调的是 `_hpBar.setData(...)` —— 外部单独刷蓝时用 `setMp` 会刷到血条上。
`setData()` 自己那一路（`:250-251`）两条都刷，所以正常显示看不出来。**不照抄这个 bug**，
本工程 `setMp` 一路没有调用者（`updateHpBy` 也只动血条，`:104-107`/`MBar:177-182`）。

## ⑫ 「查看信息」在这套代码里到底换回什么（10-15 现查）

`API.ui.clickCharacter(id)` → 客户端 `94:4:<id>` → 服务端 `handle_character_info_request` 的 action 4

```
TARGET_INFO(1284) : <对象号> : <type> : <id> : <hp> : <maxHp> : <mp> : <maxMp>
```

三档共用这一个号，靠第 3 段 `type` 分：`0` 怪（`:20215-20220`，id 段是**模板号**）、

**只认玩家档**：怪与旗两档故意不接 —— 本工程的怪身上没存服务端那个 `objectId`，
拿模板号去配会把"同种的另一只"的血填进当前目标，宁可数字不动也不填错人。
