# 维护者手册

本文给仓库维护者用，约定 PR 怎么收、怎么验证、怎么回到私有开发目录，以及发布时怎么防漏。

## 1. 仓库定位

| 仓库 | 作用 |
|---|---|
| 公开仓（本仓库） | 发布镜像；社区贡献的代码上游；不含素材和内部开发资料 |
| 私有开发目录 | 唯一完整的开发环境；有素材、夹具、内部文档和全量门 |

**公开仓 `master` 只追加提交，不再 amend / force-push。** 从第一个外部 PR 起，改写历史会让所有 fork 失效。

## 2. 一次性设置

Gitee 仓库设置：

- `master` 设为保护分支，模式选 **标准模式**
- 只允许管理员推送和合并 PR
- 如果是单人维护，不要把“必需评审人数”设成 ≥1，否则自己也会被卡
- Gitee **社区版没有**“禁止强制推送 / 禁止删除分支”的开关（属企业版功能）。普通成员没有推送权限，本来就无法强推或删除；管理员自身要靠仓库约定，必要时加本地 `pre-push` 钩子兜底

模板和规则：

- `CONTRIBUTING.md`：贡献范围、许可证、禁止提交的内容
- `.gitee/PULL_REQUEST_TEMPLATE.zh-CN.md`
- `.gitee/ISSUE_TEMPLATE.zh-CN.md`
- `测试/公开仓最小门.sh`：贡献者自检

## 3. PR 审查清单

打开 PR 后，先不合并。逐项检查：

- [ ] 改动单一，目的清楚，没有顺手格式化整个文件
- [ ] 不含素材、二进制、`*.dat`、字体、音频、SWF
- [ ] 不含 `.godot/`、`场景/生成/`、日志、截图大包、构建产物
- [ ] 不含本机绝对路径（Windows 盘符路径、Git Bash 的 `/d/...`、Linux 的 `/mnt/...` 等）
- [ ] 不含 `移植进度与计划.md`、`编年史`、`测试/_核对` 等内部资料引用
- [ ] 代码来源清楚，与 GPL-3.0 兼容
- [ ] 行为改动附原版依据（AS3/服务端/真值）
- [ ] UI/地图改动附前后截图和复现步骤
- [ ] 贡献者已运行 `bash 测试/公开仓最小门.sh`

有疑点直接评论要求修改，不要“先合并再修”。

## 4. 在私有开发目录验证

把贡献者的 fork 加为临时 remote：

```bash
git -C <私有开发目录> remote add pr-<用户> https://gitee.com/<用户>/naruto_godot_open.git
git -C <私有开发目录> fetch pr-<用户> <分支>
git -C <私有开发目录> checkout -b review/pr-<编号> master
git -C <私有开发目录> cherry-pick <提交>
```

然后在私有开发目录跑全量门（有素材、有夹具）。冲突在审查分支解决；解决不了的让贡献者 rebase。

通过后：

```bash
git -C <私有开发目录> checkout master
git -C <私有开发目录> merge --ff-only review/pr-<编号>
```

再回到 Gitee 合并 PR。私有仓的提交和公开仓的合并提交内容要一致；必要时用 `--author` 或 `Co-authored-by:` 保留作者。

## 5. 回灌规则（最重要）

> 公开仓合并了 PR，但私有仓没有同一份改动 ⇒ 下次发布同步会把它覆盖掉。

所以每次公开仓合并 PR 后，**立刻**把对应改动拿回私有仓：

1. 按上一节 cherry-pick 到私有 `master`
2. 跑全量门
3. 记下这次公开仓的 `master` 提交

发布前必须检查公开仓有没有私有仓未收录的提交；发现就中止发布，先回灌。

## 6. 发布硬闸

私有开发目录里有维护者工具 `开发工具/_公开仓发布检查.py`（不随公开仓分发），状态文件是 `发布/公开仓状态.json`。

发布前：

```bash
python 开发工具/_公开仓发布检查.py
```

它做三件事：

1. `git fetch` 公开仓
2. 比较公开仓 `origin/master` 和上次记录的发布点
3. 如果公开仓有未回灌提交，列出提交并中止

有未回灌提交时的处理：

```bash
# 1) 把提交 cherry-pick 到私有仓并跑全量门
# 2) 确认私有仓已包含这些改动
python 开发工具/_公开仓发布检查.py --ack-public
```

`--ack-public` 只表示维护者已确认回灌，不会自动改代码。

发布并推送成功后：

```bash
python 开发工具/_公开仓发布检查.py --record-published
```

它要求公开仓本地 `HEAD` 等于 `origin/master` 且工作树干净，然后记录新的发布点。

发布流程完整顺序：

1. 私有仓开发、提交
2. `python 开发工具/_公开仓发布检查.py`
3. 同步可公开源码到公开仓
4. 在公开仓跑 `测试/公开仓最小门.sh`
5. commit + push（普通提交，不要 force）
6. `python 开发工具/_公开仓发布检查.py --record-published`

## 7. 哪些能同步

可以同步：

- `场景/`（不含 `场景/生成/`）
- `脚本/`、`数据/`、`数据_扩展/`、`服务端/`
- `测试/`、`真值/`、`docs/`
- `开发工具/` 中没有下划线前缀的公开工具
- `素材/` 里的 `.gd`、`.tres`、`.gdshader`、`.md`

不同步：

- 所有图片、字体、音频、SWF、`*.dat`
- `场景/生成/`、`运行时/`、`.godot/`
- `.fixture*`、`.scratch/`、`_tmp/`、日志、截图
- 内部文档：进度、交接、编年史、体检、临时探针、变异脚本
- 公开仓专用的 `README.md`、`启动游戏.bat`、`project.godot`、`.gitignore`、`素材/README.md`

公开仓专用文件建议在私有仓的 `发布/公开仓/` 覆盖层维护，同步时最后覆盖；否则每次都会把发布版冲回私有版。

## 8. PR 沟通模板

合并后：

> 已合并，公开提交 `<hash>`。感谢贡献！

需要修改：

> 这条门 `xxx` 在完整环境里红了，原因是 …。麻烦按 … 修改；改完我会再跑一次全量门。

无法接收：

> 感谢提交。这个改动包含了 …（素材/来源不明/无法验证），按项目贡献规则不能合并。如果只保留代码部分，欢迎重新发一个 PR。

## 9. 安全与历史

- 不在任何 Issue/PR 里贴 token、账号、私服地址
- 发现公开仓误传素材或敏感信息：
  1. 立即删除文件并提交
  2. 评估是否需要改写历史
  3. 如果必须 force-push，提前通知所有 fork 维护者
- 历史一旦有外部 fork，优先追加修复提交，不轻易改写

## 10. 什么时候切换分支模式

现在用标准模式。满足下面任一条件再考虑“评审模式”：

- 增加了协作者，且希望他们能推仓库但不能直接推 `master`
- 团队要求所有改动必须有 PR 评审记录

评审模式会自动生成 `auto-*` 临时分支和 PR；对单人维护的发布镜像仓，只会增加清理成本。
