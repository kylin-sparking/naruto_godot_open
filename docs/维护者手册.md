# 维护者手册

本文约定本仓库的 PR 怎么收、怎么验证，以及素材和内部资料怎么只留在本机。

## 1. 仓库定位

| 目录 | 作用 |
|---|---|
| 本仓库（公开仓） | **唯一开发目录**：源码、测试、文档都在这里开发，推送到 Gitee |
| 旧私有仓（本机归档） | 保留迁移前的历史，只读，不再同步 |
| 本机工作树中的素材/内部资料 | 从旧私有仓搬来，只在本机使用，被 `.gitignore` 排除，不进历史 |

**`master` 只追加提交，不改写历史。** 从第一个外部 PR 起，改写历史会让所有 fork 失效。

## 2. 一次性设置

Gitee 仓库设置：

- `master` 设为保护分支，模式选 **标准模式**
- 只允许管理员推送和合并 PR
- 如果是单人维护，不要把“必需评审人数”设成 ≥1，否则自己也会被卡
- Gitee **社区版没有**“禁止强制推送 / 禁止删除分支”的开关（属企业版功能）。普通成员没有推送权限，本来就无法强推或删除；管理员自身靠仓库约定和本机 `pre-push` 钩子兜底

本机护栏（`.git/hooks/`，不随仓库分发）：

- `pre-push`：拒绝强推和删除 `master`
- `pre-commit`：拒绝素材、二进制、内部资料、>5MB 文件、本机绝对路径进入提交

## 3. PR 审查清单

打开 PR 后，先不合并。逐项检查：

- [ ] 改动单一，目的清楚，没有顺手格式化整个文件
- [ ] 不含素材、二进制、`*.dat`、字体、音频、SWF（`运行时/python/` 是随仓库分发的固定运行时，不在此列）
- [ ] 不含 `.godot/`、日志、截图大包、构建产物
- [ ] 不含本机绝对路径、token、账号、私有服务端数据
- [ ] 不含 `移植进度与计划.md`、`编年史`、`测试/_核对` 等内部资料引用
- [ ] 代码来源清楚，与 GPL-3.0 兼容
- [ ] 行为改动附原版依据（AS3/服务端/真值）
- [ ] UI/地图改动附前后截图和复现步骤
- [ ] 贡献者已运行 `bash 测试/公开仓最小门.sh`

有疑点直接评论要求修改，不要“先合并再修”。

## 4. 在本仓库验证 PR

把贡献者的 fork 加为临时 remote（不要动 `origin`）：

```bash
git remote add pr-<用户> https://gitee.com/<用户>/naruto_godot_open.git
git fetch pr-<用户> <分支>
git checkout -b review/pr-<编号> master
git cherry-pick <提交>
```

本机已有素材、烘焙图和运行时，可以直接跑相关门。通过后：

```bash
git checkout master
git merge --ff-only review/pr-<编号>
git push origin master
```

再回到 Gitee 合并 PR。合并前确认 PR 内容和合并后的提交一致；需要保留作者时用 `--author` 或 `Co-authored-by:`。

## 5. 合并后

本仓库就是开发源，**没有回灌步骤**。外部 PR 合并进 `master` 后即完成；旧私有仓归档不再接收同步，也不需要在两边维护同一份改动。

## 6. 发布前检查

发布就是推送 `master`。推送前：

1. `git status --porcelain` 应只看到预期的源码/文档改动；素材和内部资料不应出现
2. 跑 `bash 测试/公开仓最小门.sh`
3. 必要时跑完整离线门和在线门（本机有素材和夹具）
4. `git push origin master`（普通推送，不要 force）

`pre-commit` 会在提交时再挡一遍素材、内部资料和大文件；`pre-push` 会拒绝非快进更新和删除 `master`。

## 7. 哪些留在本机

以下路径已写进 `.gitignore`，只在本机保留：

- `素材/` 下的图片、字体、音频、`.import`、`.uid`、`.json`、`.bak_*`
- `.fixture*`（本地服务端存档）
- 内部文档：`移植进度与计划.md`、`给接手开发者.md`、`素材增量清单.md`、`docs/编年史_*`、`docs/交接_*`、`docs/体检_*` 等
- 一次性工具/产物：`开发工具/_*`、`测试/_核对/`、`测试/截图/`、`测试/临时/`、像素基线、内部启动变体

`运行时/python/` 是唯一随仓库分发的二进制目录（Windows 版 Python 3.13 embeddable，约 21 MB），已在 `.gitattributes` 里标记为 binary，避免换行转换。升级时整体替换该目录并单独提交，不要零散改动。

**注意**：不要在这个目录跑 `git clean -xdf`，`-x` 会把素材一起删掉。

## 8. PR 沟通模板

合并后：

> 已合并，公开提交 `<hash>`。感谢贡献！

需要修改：

> 这条门 `xxx` 在完整环境里红了，原因是 …。麻烦按 … 修改；改完我会再跑一次全量门。

无法接收：

> 感谢提交。这个改动包含了 …（素材/来源不明/无法验证），按项目贡献规则不能合并。如果只保留代码部分，欢迎重新发一个 PR。

## 9. 安全与历史

- 不在任何 Issue/PR 里贴 token、账号、私服地址
- 发现公开仓误传素材或敏感信息：
  1. 立即删除文件并提交
  2. 评估是否需要改写历史
  3. 如果必须 force-push，提前通知所有 fork 维护者
- 历史一旦有外部 fork，优先追加修复提交，不轻易改写

## 10. 什么时候切换分支模式

现在用标准模式。满足下面任一条件再考虑“评审模式”：

- 增加了协作者，且希望他们能推仓库但不能直接推 `master`
- 团队要求所有改动必须有 PR 评审记录

评审模式会自动生成 `auto-*` 临时分支和 PR；对单人维护的发布镜像仓，只会增加清理成本。
