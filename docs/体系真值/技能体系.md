## 1. 技能表在哪、怎么读

**权威源**：`2.2.3/www/act_web_nya_208_isolated/dat/GameData.dat`（AMF3 二进制，2.6MB）。

- 段名 `Skill`（服务端也是这么取的：`2.2.3/tools/fake_flash_server.py:5441`）。
- **每个分组的载荷是 zlib 压缩的 AMF3 字节串**，不是直接的对象——解压后还要再解一层。
  不知道这一点会得到"每组 0 条"的假象。
- 分组内层键：职业组是 `skill`，`PetSkill` 直接是 `{宠物id: …}`，`Effect`/`ALL` 是 `jiban`/`info`。

**取数工具**：`开发工具/导出技能数据.py` → 产出 `数据/技能_原版.json`，
并打印每个字段的可用条数（只看总数会误判，见 §4）。

## 4. 名称与描述——**不在 `Skill` 段里**

> **2026-09-18 更正（这条以前记错了，导致"描述缺 122/156"的结论是假的）**
>
> 原版客户端**根本不从 `Skill` 段取名字和描述**。真源是 **GameData 顶层 `String` 段的
> `Skill` 子表**，键是 7 位补零的技能 id，值是 `{name, desc, gain}`：
>
> ```
> DataCenter.as:522   _loc3_["name"]           = StringTool.getSkillString(id);
> DataCenter.as:535   _loc3_["effectInstruction"] = this.getSkillDesc(id, level);
> StringTool.as:114   getSkillString → ImgUtil.getImg(ImgType.String_, "Skill")
> ```
>
> 那张表实测 **96 条**，**5 个页签会显示的全部技能都命中**——详情区要显示的东西原版一直都有，
> 只是从没被导出过。已解出 `数据/技能文案.json`（工具 `开发工具/导出技能文案.py`）。
>
> 描述是**模板**，占位符要按 `DataCenter.getSkillDesc` 的规则替换（且 AS3 的
> `String.replace(字串,字串)` 只换**第一处**）：
> `valueBase`=「(值+100)/100」、`valueLevel`/`attrLevel`/`defLevel`/`probLevel`、
> `timeLevel`=值/1000、`valueTotal`=attrLevel×等级（只有它随等级变）、`triggerSkill`=技能名。
> 全部走 AS3 `Number.toPrecision(2)`——那是**有效数字**不是小数位，12→"12"、2→"2.0"、
> 200→"2.0e+2"。真机已核：体能强化 attrLevel=12 → "多提高血量上限12点"。
>
> **「需要等级」取的也不是技能自己的 `open.reqLevel`**：`SkillDataTool.as:609` 是
> reqBook 为 0 时用 `open.reqLevel`，否则查**那本技能书道具**的 `info.reqLevel`。
> 真机：体能强化 两者都 7；带土·雷霆豪火球 技能写 1、书 06000129 写 60 → 显示 **60**。
>
> **「攻击范围」显示的是文字不是数字**：`DataCenter.as:534` 是
> `CN.SKILL_ATTACK_DISTANCE[range]`，`_1.._5` = 无/近距离/远距离/中距离/超远距离。
> （旧文写的"attackRange 原样"不对。）「攻击目标」才是 `CN.SKILL_ATTACK_RANGES[target]`
> = 无/单体/范围/自己，特例 id 4012 显示"单体/范围"。

GameData 的 `Skill` 段里 `info.desc.name` / `info.desc.desc` 大量为空，实测：

| 字段 | GameData 可用 | 备注 |
|---|---|---|
| 名称 `info.desc.name` | **93 / 156** | |
| 描述 `info.desc.desc` | **34 / 156** | |
| 需要等级 `info.open.reqLevel` | 96 / 156 | 原版「学习方法」那行 |
| 需要秘笈 `info.open.reqBook` | 93 / 156 | 指向**技能书道具** id |

**客户端烘表那层是坏的**：`导出游戏数据.mjs:137` 写的是 `描述.skillDesc || 描述.desc`，
**从没读过 `String.Skill`**，所以 `数据/技能.json` 里 132/150 条描述是空的或占位的 `"XXXX"`。
（名称那列它倒是取对了：`取名称("Skill", 编号)` 就是查 `String.Skill`。）
→ 已改为读 `数据/技能文案.json`，见上面那条更正。

其它可补来源：

- `naruto-client/assets/skill_strings.json`（**96 条**）：真描述，且带 `valueLevel%` 之类的
  **模板占位符**（要拿技能自己的 `info.type_attr.valueLevel` 去替换才是最终文案）。
- `naruto-client/assets/skill_meta.json`（165 条）：`{type, range, target, name, desc, reqLevel, bookItem}`。
- `2.2.3/tools/patch_skill_effects_gamedata.py`：**项目叠加层**，手写了 `0009029`-`0009033`
  那 5 个"特别技能"的名字与完整描述（影分身之术 / 多重影分身之术 / 飞雷神之术·瞬 / 飞雷神之术·标 …）。
  这正是客户端**完全缺**的那 5 个。

**合并策略（建议）**：名称取 GameData → 客户端表 → naruto meta；描述取 GameData → naruto strings
（替换 `valueLevel%`）→ 叠加层；**任何一级都没有时留空，不要填 "XXXX"**。

## 6. 功能与数值

一条技能记录的完整形态：

```
{技能id}:
  icon   : {value:{className,swfName}, origin:{x,y}, z}      # 图标
  info   :
    desc      : {skillType, range, target, name, desc, oppositeSkill, xinfa}
    cool_down : {cdBase, cdLevel?}                            # 冷却，随等级
    consume   : {…}                                           # 消耗（查克拉/精华等）
    open      : {reqLevel, reqBook}                           # 学习条件
    type_attr : {type, valueBase?, valueLevel}                # 属性型：数值成长
    type_attack:{trigger:{probBase,probLevel}, effect:{type,valueBase,valueLevel,timeBase,timeLevel}}
  hit    : {帧:{序号:{value:{className,swfName}, origin:{x,y}, delay}}}   # 命中特效帧
  effect / action / triggerSkill                              # 特效与触发
```

**属性型 `type_attr.type` 实测取值**（14 条）：
`maxhp`×4、`maxmp`、`atk`、`def`、`avd`、`bsk`、`attack_twice_on_attack`、`damage_reduce_for_bsk`、
`couple_eat`、`couple_mob_exp`、`couple_heal_rate`。

**攻击型 `type_attack.effect.type` 实测取值**（104 条，取前 10）：
`attack`×55、`couple_protect`×4、`knock_back`×4、`atk_buff`×4、`cure_hp`×3、`add_atk`×2、
`move`×2、`reduce_atk_speed`×2、`summon`×2、`suck_hp`。

**数值是"基础值 + 每级成长"两段式**（`valueBase` / `valueLevel`），
冷却同理（`cdBase` / `cdLevel`）。描述模板里的 `%valueLevel%`、`%defLevel%` 就是取这些。

## 7. 技能树与页签（易错点）

> **2026-09-18 重写**：这一节原来三条结论里有一条半是错的（"共用一张底图是根因"、
> "同名会重复"）。已按 AS3 源码 + 逐格真机实测（66 格）重写。

### 7.1 页签 ↔ 元件 ↔ 数据，三者**不是按名字线性对应**的

`SkillWindow.as:100`：

```as3
this.tabBtns = [this.tabBtn1, this.tabBtn2, this.tabBtn4, this.tabBtn3, this.tabBtn5];
```

**显示顺序是 1,2,4,3,5**。所以：

| 屏幕第几个 | 页签名 | 按钮 | 元件 | 数据 |
|---|---|---|---|---|
| 0 | 职业忍术 | tabBtn1 | SkillPane1F（符号 930） | `groups1` = `getSkillIdsForJob(job, 0)` |
| 1 | 世界忍术 | tabBtn2 | SkillPane2F（885） | `groups2` = page 1 |
| 2 | **其他忍术** | **tabBtn4** | SkillPane4F（886） | `groups4` = **page 3** |
| 3 | **奥义禁术** | **tabBtn3** | SkillPane3F（931） | `groups3` = **page 2** |
| 4 | 特别技能 | tabBtn5 | SkillPane5 | `groups5` = page 4 |

`技能分页.json` 的旧版就是没算这一步，把 page2/page3 两张表按名字对反了。

### 7.1b ⚠️ 数据序 ≠ 视觉列序（2026-09-19 修）

`SkillPane.setData` 是 `cells[i].setCellValue(param1[i])`，**下标对着下标**，所以
「第 i 个技能」必须对上「第 i 个格子」。这两条顺序都要照抄 AS3，**不能自己按视觉排**：

- **数据序** = `DataCenter.getSkillIdsForJob(job, page)`（`开发工具/读符号时间轴.py` 读不到，
  要读 AS3）。落地在 `数据/界面/技能分页.json` 的「技能序」（扁平清单）。
- **格子序** = 各元件时间轴上 `cell0..cellN` 的**声明序**（SkillPane4F 的 cell8..11 是
  `newCell()` 另建的）。落地在 `数据/界面/忍术树_箭头与元件.json` 的「格」。

两页容易错（旧版就是这么错的，图标整体错位）：

| 页签 | 数据序 | 格子序 | 坑 |
|---|---|---|---|
| 奥义禁术 | 3 + 4 + 4 + 2 | x13(3) → x62(4) → **x171(2)** → **x122(4)** | `cells[]` 先声明 x171 那一列，**视觉从左到右却是 x122 在前** |
| 其他忍术 | 家族 8（4 条链，每链上下相邻）+ 羁绊 4 | (19,43)(19,113)(70,43)(70,113)… 再 (19,210)(70,210)… | 视觉每列是「Acv / Psv / 羁绊」三条，**按列摊平会把羁绊插进家族中间** |

其余三页（职业忍术/世界忍术/特别技能）列序恰好等于数据序，所以旧版只有这两页出错。

### 7.2 各页签的格数**不同**，由元件决定、不由技能数决定

| 页签 | 元件 | 格子数 | 列（每列自上而下） |
|---|---|---|---|
| 职业忍术 | SkillPane1F | 15 | 6 / 3 / 3 / 3 = Passive1-6 / 该职业 Attack1-3 / ProbDefence1-3 / ProbAttack1-3 |
| 世界忍术 | SkillPane2F | 18 | 6 / 6 / 6 |
| 其他忍术 | SkillPane4F | 12 | 家族忍术 8（Acv/Psv 上下成对＝4 条升级链）+ 羁绊忍术 4（couple3-6） |
| 奥义禁术 | SkillPane3F | 13 | 3 / 4 / 4 / 2 |
| 特别技能 | SkillPane5 | 8（只有 5 个技能，另 3 格是空框） | 4 × 2 |

- **技能按格子顺序摆**：`SkillPane.setData` 就是 `cells[i].setCellValue(param1[i])`。
  列表比格子短时多出来的格子**照样画**，只是空的。
- **逐格真机实测**（坐标 + 技能名 + id）：`数据/界面/忍术树_真机实测.json`；
  客户端摆格用的元件/坐标表：`数据/界面/忍术树_箭头与元件.json`。
- 坐标来源：`SkillPane1F/2F/3F` 的 `cells`（`naruto-client/assets/skill_cells.json`）、
  `SkillPane4.as setCellXY()`、`SkillPane5.as createCell()`。
  ⚠️ 那份 `skill_cells.json` 里 **SkillPane4F 那条是错的**（只有 8 条、整体偏 -20），别用。

### 7.3 三条已证伪的旧结论

1. ~~"客户端 5 个页签共用一张底图是乱填的根因"~~ —— **共用确实不对，但根因不是它**。
   客户端那张底图的元件就是 `SkillPane1F`（与符号 930 逐像素差 4.34%，只差抗锯齿），
   正是「职业忍术」页该用的。真正的根因是**另外 4 页也套用了它的格坐标**。
2. ~~"同一技能名在树上会重复（水遁·水之刃 ×2、怪力 ×3），那是升级链"~~ —— **错了**。
   那是旧实测的**坐标点偏了**：15 个点里有 6 个没落在格子上、反复点到同一格。
   **原版树上没有重复条目。**
3. 旧实测把 0001002/0001003 写成「仙斗·罡气 / 仙斗·查克拉手术」，
   放大核对是「仙法·聚气 / 仙法·查克拉守护」。

### 7.4 树的画法：两处"扁平导出 ≠ 运行画面"

- `SkillCellF`（符号 130）的**第 1 帧就是橙色选中环**；未选中的格子是
  `SkillCell_background`（符号 125，40x40 棕框）。扁平导出走第 1 帧，
  所以直接拿元件 PNG 当底图会**每一格都是橙圈**。
- **连接线**运行时带 `Style.getDisableFilter()`（亮度矩阵 0.3086/0.6094/0.082）：
  技能没学是灰的，学了才橙（`SkillPane.onEnterFrame`）。
  它和**未学技能的图标**用的是同一个矩阵——所以"未学图标"要的是**按亮度转灰**，
  不是调暗（图标美术是"彩色底 + 白色主体"，转灰后彩色底贴近格底、白主体仍是白，
  看上去就是一张纯黑白图）。
  **箭头美术本身就是橙的**，不需要把灰的调回橙；`arrows[i]` 跟着 `cells[i]` 学没学走，
  实例名 `arrowN` 的 N 恒等于 i。逐条坐标+缩放见 `数据/界面/忍术树_箭头与元件.json` 的「箭头」。
